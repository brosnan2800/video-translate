# video-translate 技术设计（原理级）

> 本文档回答「为什么这么设计」，而不是「哪段代码调了哪个接口」。
> 它和 `specs/`（契约：行为应当如何）、`adr/`（取舍：为什么选 A 不选 B）是
> 三个互补层次：spec 说"做什么"，adr 说"为什么这么选"，本文说"背后的原理
> 与机制，以及 V1→V2→V3 是怎么一步步走到今天的"。

---

## 1. 引言与目标

video-translate 解决一个很具体的问题：**把一段视频变成可导入剪映的中英双语字幕**，
而且要让字幕和声音严丝合缝地对齐，翻译尽量自然。

它不是一个"大而全"的转录平台，而是一条**窄而深的流水线**：

```
视频 → 转写 → 翻译 → 生成字幕
```

整条流水线的灵魂只有一句话：

> **时间戳是声学事实，一旦由转写产生，下游任何环节都绝不重算。**

翻译只碰文字，断行只切词、裁尾随静音，**任何一步都不去"估算"或"修正"时间**。
这就是为什么项目敢于用字节级 golden 回归来守住输出——因为输出是输入的纯函数。

本文读者：想理解架构与一个字幕断句机制的人；以及未来的维护者（知其然，更知其所以然）。

## 2. 技术架构总览

### 2.1 三阶段流水线

```
video ──transcribe──▶ segments_en.json ──translate──▶ zh_segments.json ──generate──▶ *.srt / *.txt
   (faster-whisper           ({index:en_text})          ({index:zh_text})        (纯函数，字节稳定)
    large-v3, CPU/int8,
    词级时间戳)
```

- **transcribe**：用 faster-whisper 把音频切成 `segments_en.json`，每项形如
  `{start, end, text, words:[{word,start,end}]}`。大视频按 `chunk` 切块、每块
  原子落盘 `chunk_N.json`，断点可续跑。
- **merge**（transcribe 内部最后一步）：把 Whisper 吐出的碎 cue（一句话被切成
  好几段）按语义重新拼成完整句子。
- **split**（merge 之后，V3 新增）：成句之后，按词边界断行，并把被吞掉的静音拆出来。
- **translate**：把英文段映射成中文。默认 `--engine agent`——CLI 不翻译，而是
  生成一份"翻译任务文件"交给调用方 Agent（它自带 LLM）；`--engine google` 走
  无头兜底。
- **generate**：把英文段 + 中文映射，纯函数地生成 4 个字幕文件。

### 2.2 两条贯穿全局的原则

1. **时间戳不重算（Hard rule #1）**
   下游拿到的每一个 `start`/`end`，要么是词级声学边界，要么是从上游原样取来的
   段级边界；merge 取"组内首词 start / 末词 end"，split 取"词真实边界"，generate
   用 `--gap` 只裁尾随静音。没有任何一步用"平均""偏移补偿"" heuristc 修正"。

2. **纯函数化（generate 的哲学）**
   `generate` 不联网、不加载模型，输入相同必输出相同。这是字节级 golden 回归的
   根基：只要 `build_outputs(segments, zh, gap=...)` 的输出变了，测试立刻红。
   `merge` 同理——它只"平移"边界（取真实边界），不"计算"边界。

### 2.3 V3 新增的 `words` 词级时间轴如何贯穿

```
transcribe  (word_timestamps=True)  ──▶  segment.words:[{word,start,end}]
        │                                     │
        ▼                                     ▼
merge._emit  ── 收紧到 首词start/末词end ──▶  merged.words (拼接、排序)
        │                                     │
        ▼                                     ▼
split  ── 在词边界切（_split_by_gap / _split_by_length）──▶  subcue.words (切片跟随)
        │                                     │
        ▼                                     ▼
generate.build_outputs  ── 取 首词start/末词end 作 cue 窗口 ──▶  SRT 时间戳
```

`words` 一旦在转写阶段产生，就一直跟着数据往下走，每一阶段要么携带它、要么
基于它收紧边界，**绝不丢弃后另造**。（退化路径：缺 `words` 时回退段级边界，V2
黄金因此无需重做即可兼容。）

## 3. 技术原理

### 3.1 转写与词级对齐

faster-whisper 基于 CTranslate2（把 Whisper 的 PyTorch 模型转成高效推理格式），
在 CPU/int8 下可跑，且**确定性可复现**——这是 golden 能成立的前提（见 ADR-001）。

Whisper 这类模型先把音频过编码器，再由解码器自回归地吐 token。问题在于它吐出
的是"段落"和"文字"，**段落的时间戳是模型对边界的估计，常夹杂 VAD 填充的静音**
（`speech_pad_ms`，本项目设 200ms）：也就是说，段级 `start` 往往比真正的第一个
字的起点早几百毫秒。这就是用户感知到的"字幕提前跳出来"的来源。

开 `word_timestamps=True` 后，模型额外给出**每个词**的起止时间。词边界是比段
边界更细的声学事实：句子开头那个词的 start，才是真正的"人开始说话"的时刻。
于是我们只需要在下游用"首词 start / 末词 end"替换"段级 start / end"，就能把
那段前导静音裁掉——**不需要任何估算，只是换一个更准的事实**。

### 3.2 静音为什么会被吞，又怎么吐出来（issue #001）

用户亲耳听到视频里多处明显停顿（多短场景串接），但旧版字幕把相邻场景"焊"在
一起、没有空隙。我们用 `ffprobe silencedetect` 量过真实样本：场景间确实有
~1–1.4s 的真实静音；而 faster-whisper 吐出的段里，这些静音被并进"长段"内部，
段与段之间 gap=0。

这就是 issue #001 的真问题：**不是音频密，是 ASR 把真实静音咽下去了**。

两种修法：

- **A（V3 采用）**：用词级时间戳。长段内部词与词之间的停顿，如果超过阈值
  （`DEFAULT_SPLIT_GAP = 1.0s`），就在那里把 cue 断开。真实静音于是"复活"成
  两个 cue 之间的空隙。**完全基于声学事实，不造间隙。**
- **B（兜底）**：`--gap` 在 generate 阶段钳制相邻 cue 的尾沿，保证至少留 `gap`
  秒间距、不重叠。它**只裁尾随静音，永远不凭空造间隔**——如果真实间距已经大于
  `gap`，它不动（见 §4.5）。

A 从源头修，B 兜底。V3 两者都要，但 A 为主、B 为辅。

### 3.3 剪映 42 字行宽与"先成句、再断行"

剪映（以及多数字幕软体）单行显示宽度有限，经验上限约 **42 个中文字**——超过
就换行或被挤。所以生成字幕时，每段不能太长。

但"断行"和"成句"是两件事，优先级不同：

- **成句（merge）**：语义优先。把碎 cue 拼成完整可读的句子，依据是句末标点
  （`.!?`）、相邻 gap、单 cue 时长上限。
- **断行（split）**：可读性优先。成句之后，若句子超过 42 字，**只在词边界**把
  它切成多条短 cue，每条 ≤ 42 字。绝不在词中间切断（那会破坏单词、也破坏朗读节奏）。

顺序**不可逆**：先 split 再 merge 会得到一堆读不通的碎片。所以流水线强制
"merge 在前，split 在后"（见 Spec 13 不变量）。

### 3.4 确定性 vs 质量：CPU/int8 的取舍

大模型在 GPU 上更快，但本项目机器无 NVIDIA CUDA，且 CTranslate2 不支持
AMD/Metal。于是强制 `cpu/int8`（ADR-001）。代价是转写慢（约 1× 实时），换来
三件事：**低内存、可复现 golden、纯本地无外网依赖**。对一个"跑一次出字幕"的
工具，这是正确权衡。

## 4. 翻译断句的整体机制（核心章）

这一章是用户最关心的：一个视频进来，字幕是怎么一段段"长"出来的。

### 4.1 为什么"先 merge 再 split"

Whisper 的输出天然是碎片化的：一句话常被切成 3–5 个 `segments`，每个只有半句。
如果直接拿去翻译和显示，会很碎、很难读，且逐碎片翻译会丢失上下文。

`merge` 把碎片**按语义**重新拼成完整句子：

- 若当前组最后一段以 `.!?` 结尾 → 视为句末，不再并入下一段；
- 若下一段与当前组间隔 `gap < 0.5s` 且总时长 `<= 8s` → 并入（同一句还在继续）；
- 否则断开，开新句。

拼好后，`split` 才上场：成句若太长（> 42 字）就断行。

**为什么顺序不能反**：先断行会把半句话切成"上半 / 下半"，merge 再也拼不回
完整语义句。所以代码里 `apply_merge` 一定是 merge → split 串联，且 `--no-merge`
会跳过整段、`--no-split` 只跳 split。

### 4.2 句末标点判定

`merge` 用正则 `[.!?]\s*$` 判断一段是否结束句子。中英文标点都覆盖 `.!?`（中文
句号`。`虽不在正则里，但实践中 faster-whisper 对中文也常输出 `.` 或留空格；
这是已知近似，详见 gotchas）。例外：如 `Mr.` 这类缩写会被误判，但转录文本里
极少，且下游 merge 还有 gap/dur 兜底，影响有限。

### 4.3 三个阈值的真义

| 阈值 | 默认 | 真义 |
|------|------|------|
| `merge_max_gap = 0.5` | 0.5s | 相邻碎片间隔小于它 → 视作同一句延续（同句拼接） |
| `merge_max_dur = 8.0` | 8.0s | 单 cue 时长上限，防一句话拖太长 |
| `merge_max_chars = 42` | 42 字 | **行宽，不是成句条件**——只在 split 阶段用于断行 |

注意 `merge_max_chars` 在 V2 里是"为 V3 预留"的保留字段，V3 才真正启用。
它**不参与 merge 的拼句决策**（拼句看的是 gap/dur/标点），只决定成句之后要不要
断行。这一点在 `merge.py` 注释里写死，避免后人误把它当拼句门槛。

### 4.4 词级 `split_by_length`：如何切、何时不切

成句后若 `len(text) > 42` 且带 `words`，就调用自写的 `_split_by_length`：

- 顺序累加词的字符数，`cur_len + 下一词长度 > 42` 时，把当前累积的一组切出，
  开新组；
- **永远在词边界切**（组由完整词组成），绝不切词中；
- 若某组因前面词的累计恰好略超 42（如 "the lazy dog" 显示 12 字但词长累计 10），
  也不再细分——细分就得切词，而切词比"多几个字"更伤可读性。

切出来的每条子 cue，`start/end` 直接取该组**首词 start / 末词 end**（真实边界，
不重算），`words` 切片跟随。于是子 cue 的时间戳天然准确。

### 4.5 静音保持：不重算时间戳

（对应 §3.2 的 issue #001）

`split_long_cues` 内部顺序：

1. **`_split_by_gap`**：遍历词的间隔，凡是 `下一词.start − 当前词.end > 1.0s`
   就在那里断开。这正是把被吞掉的真实场景间静音"吐"出来的动作——**完全基于
   词级声学事实，不造任何间隙**。
2. **`_split_by_length`**：对每个 gap 组，若仍超 42 字，再断行（4.4）。

`generate.build_outputs` 的 cue 窗口也用 `首词 start / 末词 end`；并叠加 `--gap`：

- pass1：每个 cue 取词边界（无词回退段级）；
- pass2：`en_i = min(en_i, next_start − gap)`，且 `en_i ≥ start_i`。
  这只裁掉尾随静音、防止重叠；若真实间距已 ≥ `gap`，`min` 不会动它——**绝不
  凭空制造间隔**。

退化路径：数据缺 `words` 时，merge/generate 全部回退段级边界，V2 黄金因此无需
重做即兼容。

### 4.6 失效模式与边界

- **`--no-split`**：保留 merge 出的整句，不断行。适合不在乎行宽、要"一句一屏"
  的场景。
- **真实静音仍被吞的残余风险**：若某段内部词间隔都 < 1.0s 但人耳觉得有停顿，
  可能是模型把停顿算进了词内——此时 `_split_by_gap` 不触发，只能靠 `--gap` 兜底
  或调小 `DEFAULT_SPLIT_GAP`（权衡：调太小会把正常换气也切断）。
- **跨 chunk 边界的 words**：每个 `chunk_N.json` 独立存词，merge 只在段级拼接；
  相邻 chunk 接缝处若恰有静音，由段级 gap 决定，不在词级细分（chunk 边界本就是
  静音切分点，影响极小）。

### 4.7 术语表如何参与（ADR-010）

术语表（txt 一行一映射 / json 字典）加载后，被**前置拼进翻译 persona**：

```
术语表（翻译时请优先采用以下译名，保持全片一致）：
- Iron Man => 钢铁侠
...
<默认 persona>
```

它是一份**软提示**，不是强制查找替换。为什么软？因为强制替换会破坏口语感与
"信达雅"——同一专名在不同语境可能有不同译法，且 LLM 更能根据上下文选词。术语表
只负责"让反复出现的名字尽量统一"，把判断权留给 agent 引擎。

## 5. 版本演进与各自的"为什么"

### V1 — 最简单的忠实迁移

- 做什么：视频 → 增量 Google 翻译 → 双语字幕。单进程、一次性。
- 为什么这么简单：先把"能出字幕"跑通，翻译质量靠 Google。
- 局限：长视频跑不完（被环境超时 SIGKILL）；断点不能续；无 agent 引擎。
- 已埋下不变量雏形：时间戳不重算（`start/end` 原样用）。

### V2 — 工程化：零配置、可续跑、agent 即引擎、片段合并

- **分块续跑**（ADR-002）：长视频切块、每块原子落盘，被杀后重跑跳过已完成块。
  为什么：环境对单进程有超时，必须能"分段跑、拼起来"。
- **CPU/int8**（ADR-001）：无 GPU，强制，换来确定性 golden。
- **仅 HTTP 代理**（ADR-003）：SOCKS 会让 huggingface_hub 崩溃；代理自动探测
  （ADR-007）。
- **agent 即引擎**（ADR-005）：默认不调 LLM，CLI 吐翻译任务给调用方 Agent（自带
  LLM），无 LLM 客户端依赖；Google 作无头兜底。为什么：翻译质量要"信达雅"靠
  真 LLM，而 CLI 不该绑死某个 LLM SDK。
- **片段合并**（ADR-004）：把 Whisper 碎片拼句，时间戳原样取（首 start/末 end）。
- **backfill**：Google 漏翻的行落 `agent_pending.json`，由 agent 补完再合并。
- 局限：段级时间戳含 VAD 前导静音（"提前"）；无断行（长句一行挤）；无静音保留
  （issue #001）；无术语表；doctor 不探 Google 可达性。

### V3 — 词级对齐 + 断行 + 术语表 + doctor 探活 + issue #001 修复

在 V2 工程底座上，把"对齐精度"和"可读性"补齐：

- **词级时间戳**（Spec 12 / ADR-008）：`word_timestamps=True`，`segment.words`
  贯穿 transcribe→merge→generate。为什么走路线 A（faster-whisper 原生，零新增
  依赖）而非引入 stable-ts？见 §6 与 ADR-008——Spike 实测 py3.13 无 stable-ts
  2.x wheel、1.0.3 损坏且不兼容，零依赖路线更契合 ADR-001 的确定性哲学。
- **断行**（Spec 13 / ADR-009）：merge 后按词边界断行（42 字），真实静音经
  `_split_by_gap` 复活。修复"提前"与 issue #001。
- **术语表**（Spec 14 / ADR-010）：软注入 persona，统一译名。
- **doctor 探 Google**（Spec 11）：转写前先确认翻译端点可达，省得跑 7 分钟才发现
  翻译阶段连不上；默认仍不硬失败（`--strict` 才返回 7）。

## 6. 决策依据与未决项

- **为什么不用 stable-ts（路线 B）**：Spike 实测 py3.13 无 2.x wheel、装 1.0.3
  会 `ModuleNotFoundError: whisper` 且未拉 torch，与 faster-whisper/int8 不兼容。
  路线 A 用 faster-whisper 原生 `word_timestamps` + 自写 `split_by_gap` /
  `split_by_length`，**零新增依赖**，更契合 ADR-001 的确定性哲学（见 ADR-008）。
- **`--gap` 定位兜底**：详见 ADR-009——词级边界为主、`--gap` 只裁尾随静音，
  否决"固定偏移"方案（会凭空造间隙）。
- **术语表软注入**：见 ADR-010——柔性统一译名，非强制替换（保口语感）。
- **未决 / 留给 V4**：
  - 跨 chunk 接缝处的词级细分（当前靠段级 gap）；
  - 句末标点对中文`。`的覆盖（当前近似）；
  - 真实停顿 < `DEFAULT_SPLIT_GAP` 但人耳明显的残余情况（需调参或换对齐后端）；
  - 黄金段级数据仍为 V2（无词），词级路径靠单测覆盖；若要端到端 golden 词级
    回归，需用真实视频重跑 V3 流水线（见 V3-STATUS）。

## 7. 术语表与索引

- **cue / 字幕块**：一条字幕（一个时间区间 + 一行或多行文字）。
- **segment**：Whisper 输出的原始段落；merge 后成为"成句"的 cue。
- **word timestamps**：每个词的起止时间，比段级更细的声学事实。
- **merge / split**：拼句 / 断行，顺序不可逆。
- **agent 即引擎**：CLI 不翻译，吐任务给调用方 Agent。
- **golden**：字节级回归基准，守住生成的确定性。
