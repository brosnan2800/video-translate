# ADR-042 — YouTube 字幕轨作为 ASR 来源（独立通道）

- **状态**：接受（待实现）
- **日期**：2026-09-17
- **关联**：[ADR-038](038-asr-layer-extraction.md)（ASR 层抽离：本项是「**第二个 Provider**」的具体化）、[ADR-012](012-acoustic-timestamp-truth.md)（声学真值 / 三 lane）、[ADR-035](035-pipeline-data-contract.md)（数据契约总线）、[ADR-003](003-http-proxy-only.md)（仅 HTTP 代理）、Spec 02（transcribe 行为）、Spec 18（verify）、[**Spec 29**](../specs/29-interface-asr-captions.md)（实现契约）、[`RESEARCH-voice-pro.md`](../RESEARCH-voice-pro.md)（P3 · yt-dlp）
- **落地**：（待实现 —— 实现契约见 [Spec 29](../specs/29-interface-asr-captions.md)）

## 背景

对**已在 YouTube 发布**的视频，重新在本机跑 Whisper 是纯浪费：YouTube 自己就存着字幕轨（创作者上传的人工字幕，或平台自动语音识别）。直接取用可省掉整段 GPU 转写。

需求方（2026-09-17）已给定四条约束：① 字幕来源优先级按人工 CC > 自动 ASR，**都没有就报错**（不回退本地转写）；② **不下载音频**；③ 词级/置信度缺失不自动补救，交人工处理；④ 做成**独立通道**，不塞进现有 Whisper 流程。

已核实的事实：

- **不能用官方 API**：YouTube Data API v3 的 `captions.download` 需要 OAuth 且**只对频道主自己**开放，他人视频直接 403；`captions.list` 只返回清单不给内容。
- **只能走非官方通道**：`yt-dlp` / `youtube-transcript-api` 同属「自爬 `timedtext`」路线。**家宽出口基本可用，云厂商出口 IP（AWS/GCP/Azure/CF Workers）被大面积标记**（PO token + IP 白名单）；2023 年起裸请求常返回空。
- **兜底事实**：视频没有字幕轨时，任何「取字幕」方案都拿不到东西 —— 唯一出路仍是本地转写（即现有 Whisper 路径）。
- **Voice-Pro 不是同类**：它用 `yt-dlp` **下载视频**再跑自己的 Whisper，本质等于本项目的 P3 + 现有流程；本 ADR 走的是「取现成字幕」，两者不可互相参考实现。
- **`baoyu-youtube-transcript`（宝玉 · `JimLiu/baoyu-skills`）是同类，且是目前最成熟的参考实现**：自研 TS CLI 直连 YouTube **InnerTube API**（零 API Key、零浏览器），双路 fallback（**换 client identity 重试** → `yt-dlp`），结果落成两层缓存（`transcript-raw.json` = 原始片段 `{text, start, duration}[]`，`transcript-sentences.json` = **按句末标点切句后的句子化结果**）。
  **但它跑在 Bun / TypeScript 上**，与本项目（Python）运行时不相容 —— 故**只能借鉴设计，不能复用代码**。本 ADR 的 D2（句子化 + 时间戳插值）、D8（降级链）、D9（缓存）均为对该实现的针对性借鉴。

## 决策

### D1. 定位：**并列的第二套 ASR 方案**（接口型），独立子命令，产出同契约

**先把定位钉死，它决定后面所有取舍的读法**：

本项目现有的唯一 ASR 方案是「**本地跑 Whisper**」——从音频出发、算力换质量、词级与置信度齐备。本项引入的是**第二套 ASR 方案**：「**通过接口取现成的 ASR 结果**」——从 URL 出发、零算力、能力集不同（无词级 / 无置信度）。

两者**并列**，不是「主 + 辅」：
- 它不是 Whisper 的加速档，也不是「有字幕时的快捷方式」；
- 它是一条**独立的能力入口**，产物（`segments_en.json`）与 Whisper 产物**同契约**，此后全链通用；
- 因此 ADR-038 的「可替换 ASR 引擎」在这里得到**第一次真实检验**：被替换的不只是 Provider 实现，而是**整条获取路径**（本地算 → 远程取）。

> **规划归属**：现有 `MAJOR_VERSION_PLAN` 的任务（T 系列）基本都围绕 **Whisper 主线**；本项是**另一条线**，不挂在 T11（ASR 层抽离）之下。plan 中的位置待定（建议单列一项「接口型 ASR 方案」）。

形态：
- 新增 `video-translate captions <url>`（名称取「取字幕」而非 `youtube`，为将来 B 站等留口）；
- 它**不做编排**，只做「URL → `<base>.segments_en.json`」，**字段与形状与 `transcribe` 产出完全一致**（ADR-035 契约表仍是唯一事实来源）；
- 与 `run_asr` 的关系：**复用 ① 层门面的后处理**（幻觉过滤 → 合并 → 补洞 → 全大写归一化），只替换「音频 → 原始段」这一步；
- **入口独立**（不走 `run <video>`）：输入是 URL 而非本地文件，且「取现成字幕」与「跑转写」是两个不同的用户意图 —— 把 URL 塞进 `run` 会让「我明明没让它转写」变成隐性长任务（见 D2）。

### 契约切点：本 ADR 要证明的东西

ADR-038 把 ① 层做成可插拔，**切点就是 `segments_en.json` 这一个契约界面**。本项不是「加一个取字幕的小工具」，而是**往已切开的层里接第二个上游**：

```
① ASR 方案层（ADR-038 已切开的区域）
                                                        可产出的能力
  本地视频 ─→ FasterWhisperProvider                     words[] ✅  置信度 ✅
              分离→转写→对齐→幻觉过滤→合并→补洞→归一化
                                                              │
  YouTube URL ─→ YtCaptionProvider（本项新增）                │
              取字幕(人工CC>自动ASR，无则报错)                 │
              →句子化+时间戳插值                                │
              →【复用】①层后处理：幻觉过滤→合并→归一化         │
                                                         words[] ❌  置信度 ❌
                                                              │
                                                              ▼
              ╔══════════════════════════════════════════════════════╗
              ║  ★ 契约切点（唯一交接面）                             ║
              ║    <base>.segments_en.json                          ║
              ║    —— ADR-035 契约表是唯一事实来源                    ║
              ╚═══════════════════════┬══════════════════════════════╝
                                      │  从这里往下两条来源完全同路
② 字幕交付层                          ▼
        P2 translate（LLM 直连 / Agent 停点 A）← 取完字幕直接到这
             → generate（4 产物）→ verify（三 lane；见 D7）
```

**这张图验证「切开」是否成立**：

| 检查 | 结论 |
|---|---|
| ② 层要不要改 | **不用** —— 它只认 `segments_en.json` |
| `translate` / `generate` | **不用** —— 分别读 segments / zh |
| `pipeline` 位置解析 | **基本不用** —— 靠产物文件判断（有 segments → 下一步 translate）|
| `verify` | ⚠️ **唯一要改的**（见 D7）|
| 真正新增的代码量 | **只有两处**：Provider（取 + 句子化）+ 子命令壳 |

**两个实现约束**：

1. **`captions` 的收尾必须对齐 `run` 的语义** —— 写 segments → 落 state → 打印 NEXT（或 exit 6 挂起等 Agent 翻译），使 P1→P2 之间**不存在第二套协议**；
2. **必须落 state 的 `segments_sha`** —— 否则 `generate` 的 stale-translation 闸会把「刚取的字幕」误判成「翻译是旧的」。

### D2. 字幕来源、语言与失败语义

- **优先级**：人工 CC（`manual`）> 自动 ASR（`auto`）。同一语言两者都有时取人工。
- **语言**：默认取 `en`（本项目主线是中英双语字幕）；`--lang` 可指定，例如取日文轨后交给 `--style` 之外的流程。
- **无字幕即报错**（需求方明确）：报 `[captions]` + 视频 id + 可用轨道清单（若有），**exit 非 0 且不写任何产物**；**静默回退本地 Whisper** 被明确禁止 —— 那会让「我明明没让它转写」变成隐性长任务。
- **自动轨的滚动形态**：YouTube 自动字幕常是 2–3 词一条、带时间重叠。**必须先句子化**，做法参考 `baoyu-youtube-transcript`（它把这一步当成核心设计，值得直接抄）：
  1. 按**句末标点**切句（`. ? ! … 。 ？ ！`），并做 **CJK 感知的合并**（中文/日文语境下不能按 ASCII 标点简单切）；
  2. 跨片段合并成完整句后，**时间戳按字符长度比例插值分配** —— 而不是取首尾片段的绝对时间。
  第 2 点是关键：它保证合并后的时间轴**单调、连续、与文本长度成比例**，不会出现「半句话被钉在整段开头」的荒唐窗口。虽然这些时间戳本来就不是声学真值（D3 已接受），但**成比例**至少让表现层（`tail` / `min_dur` / 折行）有合理依据。

### D3. 不下载音频 —— 这划出了本方案的能力边界

音频只存在于远端，「接口型 ASR」天然拿不到本地方案中基于音频的那部分能力。**这是方案性质，不是实现偷懒** —— 所以下表读作「**两套方案的差异**」，而非「本方案的待修缺陷」：

| 能力 | Whisper 方案（本地 · 有音频） | **本方案（接口型 · 无音频）** |
|---|---|---|
| `words[]`（词级时间戳） | ✅ | ❌ 引擎不产出 |
| 置信度字段（`avg_logprob` / `no_speech_prob`） | ✅ | ❌ 引擎不产出 |
| 幻觉守卫 | 五信号齐 | 靠几何 / 文本信号的几条**仍生效**；靠 ASR 自评的**自动 inert**（ADR-020 向后兼容口径） |
| `merge` 的 V8 智能断句 | 依赖词间气口 | **退化为贪心兜底** |
| `--align whisperx`（补词级） | ✅ | ❌ 需要音频 |
| `verify` 的**声学 lane** | ✅ | ❌ 需要音频参照 |

**这张表是本 ADR 最重要的产出**：两套方案并非「同一件事的快慢档」，而是**能力集不同**。选哪套取决于你手上有什么（本地文件 / URL）与你要什么（词级精度 / 零算力）。

### D4. 词级 / 置信度缺失**不做自动补救**（需求方明确）

不引入「偷偷下载音频只为对齐」的路径 —— 那会绕回 D3 划掉的边界，让「不下载音频」这个决策名存实亡。词级缺失导致的断点粗糙，**交由人工在剪辑软件内调整**。

> **客观标注**：两套方案的产物**确有质量差异**（分段与断点的精度），本 ADR 不粉饰这一点。因此产物必须带来源标记（D6），使下游与人工都能区分「本地转写的（词级齐备）」与「接口取的（词级缺失）」，而不是让两者在磁盘上长得一模一样。

### D5. 依赖选型：`youtube-transcript-api` 优先，`yt-dlp` 留待 P3

| 方案 | 形态 | 与本需求的贴合度 | 结论 |
|---|---|---|---|
| **`youtube-transcript-api`** | 纯 Python，`fetch(id, languages=[...])` → `[(text, start, duration), ...]` | **最贴合**：返回的就是字幕条目列表，无中间文件、无解析；且内置多套 client identity（D8-L1 免费拿到） | ✅ **采纳** |
| `yt-dlp` | 纯 Python，`--write-auto-subs --skip-download --convert-subs srt` | 要先落 SRT 再解析回来（绕路）；能力远超本需求（下载音视频），而我们**明确不用** | ⏸ 留待 `RESEARCH-voice-pro` **P3**（拉片源）时引入 |
| `baoyu-youtube-transcript` | **Bun + TypeScript** 自研 CLI，直连 InnerTube，`yt-dlp` 兜底 | 设计最好（D2/D8/D9 都从它抄），但**运行时不相容**：为一条可选通道引入 JS 运行时违背本项目纯 Python 工具链的定位 | ❌ **只借鉴设计，不复用代码**（`npx -y bun` 亦不采用） |

依赖按 **R3** 进 `pyproject` 顶层 + `uv.lock` 成对提交。

> **取舍记录**：曾考虑改用 `yt-dlp`（一个工具同时支撑取字幕与将来的 P3 拉片源）。**否决**：
> 本方案**明确不下载音视频**（D3），此刻引入下载器是纯负担；且取字幕要多一次
> 「落 SRT → 再解析回来」的往返。`yt-dlp` 留待 P3（`fetch` 入口）真正需要时再引入 ——
> P3 与本文档是**两条不同的路**：P3 是「下载视频 → 本地 Whisper 转写」（词级齐备、耗算力），
> 本方案是「取现成字幕 → 不转写」（零算力、无词级）。两者可串起来用：先取字幕看值不值得做，
> 值得再走 P3 拿高质量。

### D6. 产物与来源标记

- 段文件：`<base>.segments_en.json`（同契约）。
- **来源标记**：新增 `artifact` 条目记录 `asr_source`（如 `"youtube-captions:manual:en"` / `"youtube-captions:auto:en"` / `"faster-whisper"`），落在 `vt_state.json` + 一个 sidecar。
- **为什么必须有**：D3/D4 的代价是**不可见的**——两个 `segments_en.json` 从字节上分不出是谁产的。没有标记，`verify` 就无法判断「声学 lane 该跑还是该跳」，人工也无法判断「这段断点粗糙是正常的还是回归」。

### D7. verify：把「无法验证」变成一条**显式红灯**（既不拒绝运行，也不静默放行）

**问题**：`verify` 现状在缺 `--video` 时**直接拒绝运行**（`cli.cmd_verify` → exit 2），理由写得明确：

> a partial self-check would read as a pass（部分自检不得读作通过）

**这条规矩是对的**。但本方案**天生只能做部分自检**（D3：无音频）—— 两者正面冲突。

**不能简单放宽**：那会让「内容 / 表现都过、声学压根没验」读作 full pass，正是 [ADR-041](041-verify-decoupled-from-asr-self-report.md) 反对的「装作看过它没看的东西」。

**决策**：声学层中**依赖音频参照**的子检查，在本来源下产出**一条明确的 issue**（`acoustic-unavailable`）：

| 声学子检查 | 需要音频？ | 本来源下的行为 |
|---|---|---|
| 静音跨越 / 首 cue 过早（`verify_acoustic`）| ✅ | **产 issue**（无法验证）|
| 漏检 uncovered（`find_uncovered_speech`）| ✅ | **产 issue**（无法验证）|
| **相邻重叠**（`find_adjacent_overlaps`）| ❌ 纯 cue 几何 | ✅ **照常执行**（不受影响）|

行为契约：

- 该 issue **计入 flag** → strict（默认）下 **exit 8**，报告写明「无音频参照，声学层未验证」；
- 要放行须**显式弃权**（`--no-strict`）—— 与 `--allow-degrade` 同一模式（ADR-038 裁决一：只有显式意图才可降级）；
- **不引入新退出码**，也**不引入「partial pass」这一新结论**：一条 flag 足以表达「这里没验」。

**为什么这样最好**：

1. 完全遵守「无法检查 ≠ 检查通过」—— 它把「没验」变成**红灯**，而不是绿灯；
2. 零新概念、零新退出码（退出码是项目契约，改动面大）；
3. 复用项目既有的「显式弃权」先例。

**被否的方案**：

- **拒绝运行**（维持现状）：本来源将永远无法做任何自检 —— 而内容 / 表现 lane **根本不依赖音频**，拒绝它们纯属浪费；
- **静默 skipped（不计失败）**：这正是 ADR-041 反对的伪装；
- **新增 `incomplete` 第三态 + 新退出码**：最精确，但改动面与解释成本远超收益。

> **措辞红线**：该 issue 必须精确说明「**依赖音频的声学子检查未执行**」，而不是「声学层全部未跑」—— 几何子检查确实跑了，报告本身不能误导。

**实现归属**：只改 `cli.cmd_verify` 的「缺 `--video` 即 refuse」分支（改为按上述产 issue）；`verify.py` 侧**无需改动** —— `verify_acoustic` / `find_uncovered_speech` 对空参照**已有优雅降级**（`if not silences: return []`）。

### D8. 外部失败模式：**只做零依赖的一级降级**，不引入 JS 运行时，不接第三方站

非官方通道的三种典型死法（实测观察）：上游接口变动（端点失效）、IP 被标记（云出口）、PO token 校验（裸请求返回空）。`baoyu-youtube-transcript` 的处置是一条三级链（换 client identity → `yt-dlp` → 浏览器 Cookie）。本 ADR **只取其中零额外依赖的一级**：

- **L1（做）换 client identity 重试一次**：`youtube-transcript-api` 内置多套 client 配置（web / android / ios…），反爬常只命中某一套。零新依赖、成本极低，值得做 ✅
- **L2（不做）`yt-dlp` 兜底**：需额外依赖（D5 已决定不引入），且它仍是同一条自爬路线的另一个入口，并不解决根因。
- **L3（不做）浏览器 Cookie 注入**：读取本地浏览器凭证，隐私/合规代价过高，与「本地 CLI 无状态」的定位冲突。
- **更不引入 Bun/Node 运行时去复用那个 skill 的脚本** —— 本项目是纯 Python 工具链，为一条可选通道背一个 JS 运行时得不偿失。
- **报错要可诊断**：按上游语义分类（视频完全无字幕 / 请求语言轨不存在 / 视频不可用（删除·私有·地区锁）/ 被限流或 IP 被拒 / 反爬拦截），各给一句确定性指引；
- **不接第三方中转站**（实测显示它们自己也在被上游封杀，风险会原样穿透）；失败即退出，**不写半成品产物**。

### D9. 本地缓存：同视频重复调用零网络

参考 `baoyu-youtube-transcript` 的做法：首次抓取即落盘，同视频再次运行**不产生网络请求**（仅当请求语言变化时失效；`--refresh` 强制重抓）。

理由：取字幕是网络操作且**随时可能被拒**（D8）——一旦成功就该复用，反复重抓只会加速撞限流。缓存落在 `workdir(outdir, base)` 内，与其它中间产物同级、随产物目录自然失效。

## 理由

- **省算力**：对已有字幕的视频，跳过整段 GPU 转写（本项目的转写是分钟级 + 数 GB 显存）。
- **复用而非常规**：产物与转写同契约 ⇒ `translate`/`generate`/`verify`/`pipeline` 全链复用；新增的只是「URL → 原始段」这一段，正是 ADR-038 预留插槽的位置。
- **代价显式化**：D3 的能力表 + D6 的来源标记 + D7 的 skipped 语义，三者合起来保证「降级是看得见的」，不产生「看起来正常但少了一半验证」的产物。

## 后果

- **正面**：多一条低成本入库通道；ADR-038 的「第二个 Provider」验收有了具体载体（接口可替换性的最终检验）。
- **代价 / 注意**：
  - 该通道产物**词级缺失、声学 lane 不可用**，质量下限低于 Whisper 路径；
  - 依赖 YouTube 非官方接口，**稳定性不由本项目掌握**；
  - `verify` 出现「条件性 lane」，报告与文档需同步说明（Spec 18 补注）；
  - 多一个子命令与一条 artifact 来源标记，`pipeline` 的位置解析需识别该来源（否则会把「已有 segments」误判为「已完成转写」）。
- **合规**：取用他人视频字幕涉及版权与平台 ToS 边界，本 ADR 只面向**个人低频使用**；不提供批量抓取能力。

## 未来（不在本 ADR 范围）

- **`yt-dlp` 拉片源入口**（`RESEARCH-voice-pro` P3）：与 D5 的取舍联动。
- **第二、三个 Provider 抽象**（B 站字幕 / SenseVoice）：验证 Provider 接口在多来源下的稳定性。
- **词级补全的替代路径**：若将来 D3 放宽（愿意下音频），`--align whisperx` 可直接补回词级 —— 本 ADR 不动，但留此接口不变。
- **章节切分**：`baoyu-youtube-transcript` 从**视频描述**解析章节时间戳（`0:00 Introduction` 形式）来切分内容。这**不需要音频**，对本通道天然适配，可与 `translate_task.json` 的上下文一起交给 Agent。本 ADR 不实现。
- **说话人识别**：本方案**不涉及** —— 它既不产出也不消费说话人信息。（说话人识别属 Whisper 主线的既有议题，与本方案无关；将来若要在接口型 ASR 上叠加，是有别于现有音频方案的另一个独立议题，另行立项。）
- **元数据与封面入库**：抓字幕时可顺带拿到标题 / 频道 / 描述 / 封面（参考其 `meta.json` + `imgs/cover.jpg`），对 `source` 字段与资源库有潜在价值。本 ADR 不纳入。
